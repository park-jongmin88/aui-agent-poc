# 게이트웨이 사용정리

이 프로그램에서 MLflow AI Gateway 를 어디에 어떻게 쓰는지, 그리고 judge 평가 시
게이트웨이 인증을 어떻게 처리하는지 정리한다.

<br>

## 요약

LLM 은 항상 **MLflow AI Gateway** 를 통해 호출한다. 실제 LLM 주소·키는 gateway 가
가지고 있고, 이 프로그램은 gateway 만 부른다. gateway 는 MLflow 서버 위에서 동작하며
호출 시 MLflow 계정(아이디:비번) 기반 **HTTP Basic 인증**을 요구한다. 따라서
게이트웨이를 호출하는 쪽이 매 요청에 Basic 인증 헤더를 실어야 한다.

<br>

## 게이트웨이를 쓰는 곳 (3군데)

<br>

### 1. LLM 답변 생성  ✅ 정상

- **파일**: `assets/llm.py`
- **언제**: 사용자가 대화할 때 (에이전트가 답변 생성)
- **방식**: `ChatOpenAI(base_url=".../gateway/mlflow/v1", default_headers=Basic인증)`
- **인증**: 우리 코드가 헤더에 Basic 인증을 직접 넣는다 → 통과

<br>

### 2. 게이트웨이 엔드포인트 조회/선택  ✅ 정상

- **파일**: `assets/gateway_utils.py`
- **언제**: `agent.py` 등록 시 LLM 선택, `judge_register.py` 평가 LLM 선택
- **방식**: REST 호출 (`/api/3.0/mlflow/gateway/endpoints/list`)
- **인증**: Basic 인증 헤더 → 통과

<br>

### 3. Judge 평가용 LLM  ⚠️ 자동만 문제

- **파일**: `judge_register.py`, `evaluate.py`
- **언제**: judge 가 답변을 채점할 때
- **방식**: `make_judge(model="gateway:/<엔드포인트명>")`
- **인증**:
  - **수동 평가**(`evaluate.py` 직접 실행) → litellm 몽키패치로 헤더 주입 → 통과 ✅
  - **자동 평가**(자동 트래킹, 서버가 실행) → 인증이 judge 에 저장되지 않아 실패 ❌

<br>

## 정리 표

| 용도 | 파일 | 인증 방식 | 상태 |
|------|------|-----------|------|
| LLM 답변 생성 | `assets/llm.py` | 헤더에 Basic | ✅ |
| 게이트웨이 조회 | `assets/gateway_utils.py` | 헤더에 Basic | ✅ |
| Judge 수동 평가 | `evaluate.py` | litellm 몽키패치 | ✅ |
| Judge 자동 평가 | (MLflow 서버가 실행) | 저장된 인증 없음 | ❌ |

## Judge 게이트웨이 인증 상세

<br>

### 전체 그림 (누가 누구를 부르나)

```
evaluate.py (수동 평가)
   ↓
make_judge(model="gateway:/<엔드포인트명>")   ← gateway 모델 지정
   ↓
MLflow 가 "gateway:/" 를 보고 → 내부적으로 litellm 을 호출 엔진으로 사용
   ↓
litellm 이 gateway 엔드포인트로 HTTP 요청
   ↓
[gateway 입구 = MLflow Tracking Server] ← 여기가 HTTP Basic 인증을 요구!
   ↓ (인증 통과하면)
gateway → 실제 LLM 호출 → 평가 점수 반환
```

핵심:
- **gateway 는 MLflow 서버 위에서 동작** → gateway 호출 인증 = MLflow 서버의 Basic 인증(아이디:비번)
- **gateway 모델을 쓰면 MLflow 가 litellm 을 통해 호출** → 그래서 `litellm` 이 judge 의존성

<br>

### 수동 평가 인증 — litellm 몽키패치

gateway 는 Basic 인증을 요구하는데 litellm 이 그 헤더를 자동으로 안 실어준다.
그래서 `litellm.completion` 함수를 가로채(래핑) 매 호출마다 Basic 헤더를 강제로 끼워넣는다.

동작 순서:
```
1. 아이디:비번 → base64 인코딩 → "Basic xxxxx" 헤더 문자열 생성
2. 원래 litellm.completion 을 보관
3. litellm.completion 을 새 함수로 교체 (extra_headers 에 Basic 강제 병합)
4. 비동기 경로(acompletion)도 동일 패치
5. 중복 패치 방지 플래그 설정
```

이 패치는 `judge_register.py` / `evaluate.py` 의 `_connect()` 안에서 걸린다.
성공 시 콘솔에 `[정보] litellm 호출에 Basic 인증 헤더를 주입하도록 설정했습니다.` 가 뜬다.

> 참고: `LITELLM_EXTRA_HEADERS` 환경변수 방식은 litellm SDK 직접 호출 경로에서
> 안 읽혀 실패했다(주로 litellm proxy 설정용). 그래서 함수 래핑 방식을 쓴다.
> 또 litellm 이 빈 키면 호출 전에 막는 경우가 있어 `OPENAI_API_KEY` 에 더미값을
> 넣는다(실제 인증은 Basic 헤더가 담당).

<br>

### 자동 평가는 왜 안 되나

핵심은 **"누가 gateway 를 호출하느냐"** 이다.

- **우리 코드(프로세스)가 호출** → 우리가 인증 헤더를 넣을 수 있음 → 정상
  (LLM 답변 생성, 게이트웨이 조회, judge 수동 평가)
- **MLflow 서버가 호출** → 우리 코드가 개입 못 함 → 인증 못 넣음 → 실패
  (judge 자동 평가)

litellm 몽키패치는 **그 스크립트 프로세스 안에서만** 유효하다. 자동 평가는
스크립트가 끝난 뒤 MLflow 서버가 저장된 judge 를 불러와 실행하므로 패치가 닿지 않는다.

`make_judge(extra_headers=...)` 로 인증을 judge 에 넣어두는 방법도 시도했으나,
`register()` 로 저장할 때 extra_headers 가 직렬화에 포함되지 않아(MLflow 3.13 확인)
서버가 인증 없이 gateway 를 호출하게 된다. → 권한 오류.

> 검증: `make_judge` 직후엔 judge 객체에 extra_headers 가 있으나, `register()` 후
> `list_scorers` 로 다시 불러오면 사라진다. 저장되는 데이터
> (`instructions_judge_pydantic_data`)에는 instructions/model/feedback_value_type
> 만 있고 extra_headers 는 없다. 코드 문제가 아니라 MLflow 한계.
> (진단: `check_judge.py` 로 등록된 judge 의 인증헤더 저장 여부 확인 가능)

## 재현 시 주의점

1. `_connect()` 가 gateway 호출 전에 불려야 한다 (패치가 먼저 걸려야 함).
2. 아이디:비번이 정확해야 한다 (gateway UI "Try in Browser" 의 Authorization 값과 동일).
3. litellm 버전 의존 — 메이저 버전이 바뀌면 `completion` 구조가 달라져 래핑이 안 먹을 수 있음.
4. gateway 입구 = MLflow Basic 인증 이라는 게 핵심 전제 (인증 방식이 바뀌면 패치 불필요해질 수 있음).

<br>

## 관련 파일

- `assets/llm.py` — LLM(gateway) 호출
- `assets/gateway_utils.py` — 게이트웨이 조회 공통 모듈
- `judge_register.py` / `evaluate.py` — judge 등록/평가
- `check_judge.py` — 등록된 judge 의 인증헤더 저장 여부 확인(진단)
